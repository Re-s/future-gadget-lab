## 🎯 执行策略要求（核心）

> **这是用户明确强调的硬性要求。**

### 主会话行为边界

| ✅ 允许 | ❌ 禁止 |
|---------|---------|
| 分析需求，拆解子任务 | 直接执行业务代码 |
| 选择子 agent 配置 | 直接运行构建/测试 |
| 分发任务并跟踪 | 直接处理耗时操作 |
| 收集结果并整合 | 直接搬运文件内容 |
| 向用户汇报结论 | — |
| 处理用户决策交互 | — |

### 子 Agent 规则

1. **自包含**：子 agent 看不到主会话上下文，prompt 必须包含完整背景和目标
2. **后台运行**：子 agent 默认后台运行，不阻塞主会话
3. **并行执行**：多个互不依赖的子任务在同一消息中同时派出
4. **明确交付**：每个子任务必须有清晰的交付格式和验收标准

### Token 预算

- **主会话上下文**：实验室最贵的耗材，省下来做判断与复盘
- **主会话职责**：决策、复盘、汇总
- **子 Agent 职责**：执行、验证、产出

## 📝 代码质量要求

### 命名规范

| 语言 | 变量 | 函数 | 类 | 文件 |
|------|------|------|-----|------|
| JavaScript/TypeScript | camelCase | camelCase (动词开头) | PascalCase | kebab-case |
| Python | snake_case | snake_case (动词开头) | PascalCase | snake_case |
| Rust | snake_case | snake_case | PascalCase | snake_case |
| Go | camelCase | PascalCase (导出) / camelCase | PascalCase | snake_case |

### 代码风格

1. **单一职责**：每个函数/类只做一件事
2. **DRY**：不重复自己
3. **KISS**：保持简单
4. **YAGNI**：不过度设计

### 注释规范

| ✅ 必须注释 | ❌ 禁止注释 |
|-------------|-------------|
| 复杂算法 | 注释掉的代码 |
| 业务规则 | 无意义的 // TODO |
| Hack/Workaround | 重复文档的注释 |
| 非显而易见的设计决策 | // 变量声明 |

### 错误处理

1. **不要静默吞错**：捕获异常后必须处理或重新抛出
2. **错误分级**：ERROR / WARN / INFO
3. **提供上下文**：错误信息应包含足够的诊断信息

### 函数调用日志

| # | 要求 | 说明 |
|---|------|------|
| 1 | 开发验证阶段输出所有函数调用日志 | 尽可能全量输出，以备跟踪测试 |
| 2 | 入口/出口都记录 | 函数名、调用者、参数摘要、返回值摘要 |
| 3 | 记录耗时 | 超阈值（如 >100ms）单独标记 |
| 4 | JSON 结构化 + 调用链标识 | task_id/request_id 便于关联 |
| 5 | 敏感数据脱敏 | 密码、token、密钥不落日志 |
| 6 | 性能平衡 | 热路径用采样/摘要，生产可配置关闭 |

### 依赖管理

1. **最小化**：只引入必要的依赖
2. **评估**：检查维护状态、下载量、CVE
3. **锁定**：提交 lockfile

### 测试规范

| 指标 | 最低目标 | 理想目标 |
|------|----------|----------|
| 行覆盖率 | 80% | 90%+ |
| 分支覆盖率 | 75% | 85%+ |
| 函数覆盖率 | 80% | 95%+ |

### 安全规范

- [ ] **注入**：使用参数化查询，验证所有输入
- [ ] **认证**：安全的密码存储（bcrypt/argon2）
- [ ] **敏感数据**：加密存储，不硬编码
- [ ] **访问控制**：最小权限原则
- [ ] **配置**：默认安全配置
- [ ] **依赖**：定期漏洞扫描

## 🚨 错误处理要求

| # | 要求 | 说明 |
|---|------|------|
| 1 | 错误分类 | 按严重程度（P0-P3）和类型（环境/逻辑/资源/外部/配置）分类 |
| 2 | 重试策略 | 指数退避，最多 3 次，仅对可重试错误 |
| 3 | 降级策略 | 核心功能优先，优雅降级，透明降级 |
| 4 | 异常上报 | 分级上报（CRITICAL/ERROR/WARNING/INFO） |
| 5 | 故障排查 | 标准化排查流程（收集→复现→定位→修复→复盘） |

详见 [error-handling.md](error-handling.md)

## 🐧 领域知识预加载要求

| # | 要求 | 说明 | 来源 |
|---|------|------|------|
| 1 | 领域判断前置 | 任何阶段开始前，先判断是否命中领域触发词 | 用户要求 |
| 2 | Deepin 必读 skills | Deepin 相关开发必须先阅读官方 deepin-skills 仓库 | 用户明确要求 |
| 3 | **命中时才下载** | 命中触发词才 clone/pull 仓库；未命中不占用资源 | 用户明确要求 |
| 4 | **使用前先更新** | 每次命中必须更新到 GitHub 最新版本，禁止用过期副本 | 用户明确要求 |
| 5 | **注册表模式** | preset 只存「触发词 → 仓库地址」映射，skills 明细以仓库 README 为准，不硬编码进文档 | 用户明确要求 |
| 6 | 更新失败处理 | 更新失败时告知用户缓存的提交日期，由用户决定是否继续 | 设计推导 |
| 7 | 知识注入 prompt | 将知识库要点写入子 agent prompt，保持自包含原则 | 与执行策略一致 |

**机制**：注册表位于 `workflow-preset.json` → `domain_knowledge_preload.domains`；新增领域只需追加一条 `{triggers, repo_url, cache_dir}` 注册项。
